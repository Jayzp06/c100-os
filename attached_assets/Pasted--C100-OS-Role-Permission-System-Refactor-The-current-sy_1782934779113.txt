# C100 OS — Role & Permission System Refactor

The current system models each user as having a single role.

This architecture is no longer sufficient.

Refactor the authorization model into a true Role-Based Access Control (RBAC) system that supports multiple simultaneous organizational roles and independent system administration roles.

The goal is to accurately represent how the Collegiate 100 Trailblazing Chapter actually operates while remaining configurable enough for future chapters.

---

# Core Design Principle

Separate Organizational Roles from System Roles.

Organizational Roles define a member's responsibilities within the chapter.

System Roles define what a user may do within C100 OS.

These two permission systems must remain completely independent.

Being President should not automatically make someone a Platform Administrator.

Likewise, being a Platform Administrator should not automatically make someone President.

# Executive Board Permission Model

Executive Board should function as a permission group.

Every Executive Board member inherits a shared Executive Board permission set.

Each office then inherits additional permissions specific to that office.

Example

Executive Board

↓

Shared Executive Permissions

↓

President-specific permissions

Vice President-specific permissions

Secretary-specific permissions

Treasurer-specific permissions

Chief of Staff-specific permissions

Sergeant-at-Arms-specific permissions

This prevents duplicate permission definitions while preserving office-specific responsibilities.

# Role Compatibility Rules

Prevent incompatible organizational offices.

Examples

President + Vice President

President + Secretary

President + Treasurer

Vice President + Treasurer

Secretary + Treasurer

These combinations should not be assignable unless explicitly overridden by Platform Administrator.

Committee roles, appointed officer roles, and system roles may coexist.

Switching roles should

• Never permanently change permissions

• Clearly display the active simulated role

• Allow one-click return

• Record every impersonation event in the audit log

This capability exists exclusively for development, testing, demonstrations, and platform administration.

---

# Future-Proofing

The authorization system should be entirely database-driven.

New organizational roles should be creatable without changing application code.

New system roles should be creatable without changing application code.

Permissions should also be database-driven.

Avoid hardcoded enums wherever practical.

The objective is to make C100 OS deployable to future Collegiate 100 chapters with different organizational structures while preserving the same authorization framework.

Document every architectural decision before implementation and maintain backwards compatibility with the existing platform wherever practical.
