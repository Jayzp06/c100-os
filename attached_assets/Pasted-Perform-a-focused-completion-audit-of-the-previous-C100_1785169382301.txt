## 1. Correct the update-checker error handling

The current implementation incorrectly classifies broad errors such as `failed to fetch` as `{ status: "up-to-date" }`.

That is not acceptable because a network failure does not prove that the installed version is current.

The updater must distinguish:

- Successful check with no newer version → `up-to-date`
- Successful check with newer version → `update-available`
- No published release or missing manifest → a specific release-configuration state
- Network, DNS, TLS, timeout, or GitHub availability failure → connection error
- Invalid signature or invalid manifest → verification/configuration error
- Installation or relaunch failure → installation error

Only return `up-to-date` when the updater successfully contacts the configured endpoint, parses the manifest, compares versions, and determines that no newer version exists.

Do not classify `failed to fetch`, generic 404 responses, malformed manifests, or connection errors as “up to date.”

Show clear user-facing messages for each condition without exposing secrets.
