Audit the member update endpoint and member-detail mutation payload.

Organization roles and system roles must be handled as separate sets:

- `orgRoleSlugs`
- `systemRoleSlugs`

Rules:

- Changing organization roles must not fail merely because the request also contains unchanged system roles.
- Compare the requested system-role set with the stored system-role set.
- Require `manage_roles` only when the system-role set actually changes.
- Do not treat the presence of `systemRoleSlugs` in the payload as proof of a system-role mutation.
- If system roles are unchanged, preserve them without requiring an additional system-role escalation check.
- If the caller is not allowed to change system roles, the safest frontend behavior is to omit `systemRoleSlugs` entirely.
- Updating organization roles must never silently delete an existing system role.
- Updating system roles must never silently delete organization roles.
- The entire authorized update must be transactional.

- Determine which explicit permission authorizes organization-position assignment.
- Determine which explicit permission authorizes system-role assignment.
- Platform Administrator is the account/platform administration role and should hold `manage_roles` if that matches the intended final model.

- President must not receive `manage_roles` solely because they are President.
- Do not add `isAdmin`, President, Technology Chair, or legacy-role bypasses.
- Assigning/removing `platform_admin` must require `manage_roles`.
- Assigning normal officer positions must use the intended organization-role management permission.

Verify the live production RBAC seed gives Platform Administrator the intended account-administration permission. If `manage_roles` is missing accidentally, add it explicitly and idempotently to `platform_admin` only.
