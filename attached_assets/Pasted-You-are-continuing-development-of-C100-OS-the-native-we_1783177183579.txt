Economic Development & Empowerment

- committee leaderboards

If the database says Person A is chair, all relevant interfaces must show Person A.

PHASE 6 — QR CHECK-IN SYSTEM
==================================================

The QR and rotating-code event check-in system is currently broken.

Observed problems:

- valid displayed codes are rejected as incorrect
- the rotating code is currently too long
- the QR code scans as “No data found”
- check-in must work reliably across devices

Audit the complete check-in flow:

- event creation
- event activation
- check-in session creation
- rotating code generation
- code storage
- code validation
- expiration
- QR payload generation
- QR scanning
- attendance submission
- duplicate attendance prevention
- error messages

ROTATING CODE REQUIREMENTS

The current code appears to be approximately 9 or more characters.

SHORTEN IT.

Use a short human-readable rotating code.

Recommended target:

6 characters.

Use uppercase letters and numbers while avoiding visually confusing characters where practical.

Example character set could exclude:

- O
- 0
- I
- 1

The code must be:

- short enough to manually enter quickly
- long enough for reasonable event check-in security
- regenerated according to the existing rotation interval or a sensible interval
- validated consistently by frontend and backend

Do not allow the frontend and backend to use different code-generation or normalization rules.

QR CODE REQUIREMENTS

Generate a real QR payload.

Do not render an empty or invalid QR value.

The QR payload should contain sufficient information for C100 OS to identify the event/check-in session.

Prefer an application deep link or HTTPS fallback strategy compatible with desktop and web environments.

Validate the QR value before rendering.

Implement a visible fallback if QR generation fails.

Test the complete logical flow.

PHASE 7 — EVENT VISIBILITY AND COMMITTEE AUTHORITY
==================================================

The event authorization model needs correction.

COMMITTEE CHAIRS

Committee Chairs should manage events relevant to their committee.

They may create appropriate chapter-facing events when authorized.

However, internal committee meetings must be restricted to their committee.

Separate these concepts:

EVENT VISIBILITY

Who can see the event?

ATTENDANCE ELIGIBILITY

Who can check into the event?

EVENT OWNERSHIP

Who can edit/manage the event?

Examples:

Chapter Event:
visible chapter-wide
attendance chapter-wide

Committee Event:
may be visible chapter-wide depending on configuration
attendance rules based on event purpose

Internal Committee Meeting:
visible only to the committee
attendance only for committee members
managed by the Committee Chair and authorized leadership

Do not use one boolean field to represent all three concepts.
